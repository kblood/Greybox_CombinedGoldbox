# Greybox Long-Term Goals

> Status: active program charter (2026-07-15).
>
> This document defines the durable end state and the major programs required to reach it. It is
> intentionally more stable than `ROADMAP.md` and `BUILD-QUEUE.md`: detailed substeps are added as
> retail-byte evidence exposes the real work, while the goals and verification gates remain stable.

## North Star

**Scope clarification — 2026-11-06:** research covers every Gold Box game and
its platform/release variants, including DOS, Amiga and C64. Track missing
holdings and uncertain editions explicitly. The browser Greybox and native DOS
ASM Greybox validate shared recovered formats and behavior; their code remains
in separate folders on master. The [graphics research plan](research/graphics-research-next-tasks-2026-11-06.md)
applies this scope to stable image identities, game consumers and replacement-art
provenance. An individual engine milestone does not establish all-version coverage.

Greybox becomes a clean-room, testable Gold Box platform that can identify, inspect, play, convert,
and author content for the major SSI engine families, while also producing verifiable native DOS
reconstructions.

The final product is not just a collection of game previews. A user points Greybox at legally owned
game data, Greybox identifies the title and engine family, reports its capabilities honestly, and
runs every supported system through shared, profile-driven engine contracts.

```text
Binary evidence and format corpus
              |
              v
Universal engine contracts
              |
              v
Campaign-complete game support
        /                 \
       v                   v
Native DOS track      Authoring / FRUA
       \                   /
        v                 v
     Reproducible public releases
```

## Planning Hierarchy

The project uses four planning levels:

1. **Program goals** in this file define the end state and completion gates.
2. **Milestones** in `ROADMAP.md` organize dependency order and major deliverables.
3. **Shippable slices** in `BUILD-QUEUE.md` are the current executable work.
4. **Research handoffs** under `docs/engine/research/` hold evidence, commands, offsets, and
   subsystem-specific decompile plans.

Do not turn this charter into a speculative thousand-item queue. When a milestone becomes active,
split only its next uncertain boundary into evidence-gathering substeps. Promote proven results into
implementation and verification slices.

### Cold-start contract

Conversation history is never a project dependency. A new session must:

1. Read `HANDOFF.md`, then the `BUILD-QUEUE.md` **Active execution pointer**.
2. Resume the first actionable unchecked substep under that pointer, even when older queue sections
   suggest a different order. Skip only gates explicitly labelled environment-pending, and leave
   those gates unchecked.
3. Add newly discovered substeps to `BUILD-QUEUE.md` before relying on them for later work.
4. Before ending, record the exact completed evidence, failed hypotheses, next command, and next
   unchecked substep in `HANDOFF.md` and `BUILD-QUEUE.md`.
5. Keep generated outputs reproducible from checked-in scripts; do not make `build/` artifacts the
   only surviving record of how a result was produced.

## Goal 1: Automated Decompilation and Evidence Factory

Every available game must pass through the same repeatable analysis pipeline.

### Completion gates

- Every EXE/OVR has a generated segment and overlay map.
- FBOV, TPOV, VROOMM, RTLink/Plus, resident stubs, and selector tables are resolved as far as the
  available bytes permit.
- ECL, GEO, WALLDEF, monster, item, combat, save, graphics, and audio archives receive generated
  inventories.
- Cross-game function candidates are clustered by signatures, strings, control-flow shape, and data
  access rather than absolute offsets alone.
- Reports are regenerated by scripts; manually maintained tables are either generated or clearly
  labelled as commentary over generated evidence.
- Every recovered claim records provenance: retail bytes, runtime trace, source oracle, published
  format documentation, or labelled inference.
- IDA/Ghidra projects can be recreated from documented loader settings, maps, signatures, and symbol
  import files.

### Expected evolving subprojects

- VROOMM fixup-driven segment routing: distinguish public overlay stubs from direct resident/runtime
  targets and resolve the retained ambiguous stub-array starts.
- Automatic overlay relocation and segment:offset round-tripping.
- Normalized function signatures across game revisions.
- Generated cross-game save-dispatch maps from `savgam` anchors, owning overlay procedures, and
  inbound public calls, including explicit resident-EXE and non-literal exceptions; runtime traces
  promote only execution-reached candidates to symbols.
- Narrow DOSBox-X/Unicorn trace capture around unresolved call chains.
- CoAB source-unit names correlated back to retail CoAB offsets without treating source as proof for
  sibling games.
- RTLink/Plus map and runtime-library separation for DQK and FRUA `CKIT.EXE`.

Primary execution plan: `research/decompile-handoff-gen1-gen2.md`.

## Goal 2: Universal Gold Box Runtime

Build one engine around explicit capabilities and profiles, not a growing collection of hidden
game-specific assumptions.

### Completion gates

- DAX, DAA, HLIB, GLIB, TLB, save, image, music, and sound formats have stable read contracts and
  round-trip/write contracts where authoring or conversion requires them.
- ECL dialects are profile-selected and tested directly against retail scripts.
- Exploration, encounters, combat, towns, wilderness, dialogue, inventory, magic, time, and saves
  use shared engine interfaces.
- Rulesets are plugins for AD&D 1e, AD&D 2e, Buck Rogers XXVc, and authored-module overrides.
- Graphics profiles support EGA, VGA, and Amiga assets, including runtime switching where equivalent
  assets exist.
- Unsupported or unlocated data produces a capability gap, never an invented value presented as a
  decoded fact.
- Browser, Electron, authoring, conversion, and native tooling consume the same engine-neutral data
  contracts where their runtime constraints permit it.

Profile-specific discoveries remain legitimate, but each must be represented as a named dialect,
layout, capability, or ruleset delta. Gateway's 422-byte and Treasures' 510-byte monster records,
plus their VGA tiles, are examples: they must become title-scoped Savage Frontier contracts, not
silent CoAB fallbacks.

## Goal 3: Campaign-Complete Compatibility

Support advances through explicit levels. The support page should eventually be generated from these
machine-readable gates.

| Level | Required proof |
| --- | --- |
| Mapped | Binary/container inventory plus executable anchors. |
| Preview | Dashboard plus decoded representative assets. |
| Route | Retail ECL-to-map exploration works without a synthetic map seam. |
| Combat | Retail monsters plus a naturally reached encounter/combat/resume handoff work. |
| Persistent | Original save import/export and Greybox save/reload work for the route. |
| Campaign | Major areas, transitions, towns, wilderness, quest state, and endings are reachable. |
| Verified | Automated route corpus and regression suite pass on clean inputs. |

### Promotion waves

1. Pool of Radiance, Curse of the Azure Bonds, Secret of the Silver Blades, Champions of Krynn, and
   Death Knights of Krynn.
2. Gateway and Treasures of the Savage Frontier under a shared Savage Frontier VGA/AD&D 2e profile.
3. Pools of Darkness and Neverwinter Nights DOS/AOL, preserving their later Gen1 differences.
4. The Dark Queen of Krynn as the complete Gen2 reference implementation.
5. Buck Rogers titles after retail binaries are available, using an XXVc ruleset rather than AD&D
   assumptions.
6. FRUA and user-authored modules.

Campaign-complete does not require cycle-perfect emulation. It does require normal gameplay to stop
depending on demo encounters, hard-coded monster choices, or hand-selected route seams.

## Goal 4: Native DOS Reconstruction

The ASM/native track becomes a reproducible sibling product rather than only a probe collection.

### Completion gates

- `GBBOOT`, `CCECL`, `CCGEO`, `CCCOMBAT`, and related bridges have a documented runtime contract.
- Gen1 content can be hosted by the selected native engine through reproducible conversion.
- CoK and DoK campaigns run on the DQK-generation DOS runtime with validated imports, combat entry,
  outcome, and ECL resume.
- RTLink and VROOMM maps are sufficient to replace or intercept selected original routines safely.
- Native tests capture expected screens, structured bridge records, route state, combat state, and
  output hashes under DOSBox.
- Web and native tracks consume shared generated evidence manifests where practical.
- Distributable artifacts contain only original Greybox code and require user-owned game data.

The ambitious native endpoint is not merely a retitled executable. It is a clean, documented runtime
and conversion toolchain capable of hosting the intended campaign data.

## Goal 5: FRUA-Superset Authoring Platform

Greybox Author becomes a complete content-production environment over the same runtime.

### Completion gates

- Maps, events, encounters, monsters, NPCs, items, spells, dialogue, art, sound, campaign transitions,
  and ruleset settings are editable.
- Existing FRUA modules import with a per-feature compatibility report.
- New modules may target Greybox's richer runtime while retaining a constrained FRUA export mode.
- Validation detects unreachable maps, broken event chains, missing assets, invalid references,
  impossible encounters, and ruleset conflicts.
- A module package runs identically in browser and Electron, and through native/export targets where
  their capability profile allows it.
- Packages are versioned, deterministic, migratable, and testable in CI.
- A complete small reference campaign is built with public tooling as the authoring acceptance test.

## Goal 6: Verification at Scale

Compatibility claims must remain true as support broadens.

### Completion gates

- One corpus command scans every available game and emits a machine-readable compatibility report.
- Golden tests cover representative records, maps, scripts, and graphics from every engine family.
- Browser tests cover dashboard, exploration, natural combat, combat resume, save, and reload.
- Native tests cover route setup, tactical handoff, output records, and nonblank frame evidence.
- The public support matrix is generated from test/corpus evidence or validates its manual claims
  against that evidence.
- A regression can be localized to a format, profile, ECL dialect, ruleset, subsystem, or shell.
- Local copyrighted fixtures remain optional; tests skip with explicit reasons when user-owned data
  is absent and retain synthetic clean-room fixtures for contract coverage.

## Goal 7: Releasable Product

The project must work outside the maintainer's current workstation.

### Completion gates

- Browser and Electron builds support user-selected local installations without compiled-in machine
  paths.
- No copyrighted game assets are included in public releases.
- Detection explains which files, graphic sets, and capabilities are present, missing, or unsupported.
- Saves and authored modules have version migrations, validation, and backup/recovery behavior.
- Builds are reproducible, versioned, documented, and tested on clean machines.
- Deployment is atomic and live routes are verified after release.
- The support matrix clearly distinguishes mapped, preview, route, combat, persistent, campaign, and
  verified support.

## Program Milestones

These milestones are deliberately broad. Add concrete substeps to `BUILD-QUEUE.md` as each milestone
enters active work.

### P1: Evidence Factory

One command analyzes all installed games and regenerates binary maps, archive inventories,
capability gaps, cross-game signatures, and support evidence.

Exit gate: a changed or newly installed binary can be incorporated without manually reconstructing
the analysis process.

Manual original-DOS fixtures that cannot be synthesized cleanly are tracked in
`MANUAL-TEST-REQUESTS.md`; each request includes an exact pre-save state, capture command, acceptance
check, and clean-room handling boundary.

### P2: Natural Gameplay Vertical Slices

Pool, CoAB, Secret, CoK, and DoK each demonstrate:

```text
retail area entry -> exploration -> natural encounter -> combat
                  -> outcome -> ECL resume -> save -> reload
```

Exit gate: no hard-coded preview monster or synthetic combat trigger is needed for the tested route.

### P3: Savage Frontier Profile

Recover Savage Frontier VGA graphics, monster/item layouts, AD&D 2e deltas, and natural encounter
handoff. Promote Gateway first, then reuse the proven profile for Treasures.

Exit gate: Gateway reaches Combat and Persistent support; Treasures reaches at least Route support
without borrowing invalid CoAB/Krynn assumptions.

### P4: Campaign-Grade Gen1

Complete area transitions, towns, wilderness, quest-state persistence, save parity, and ending paths
for the first promotion wave.

Exit gate: automated route scripts can traverse representative early, middle, and ending campaign
states for each promoted game.

### P5: Gen2 and Native Convergence

Finish DQK runtime contracts and use the recovered Gen2 behavior to advance native CoK/DoK hosting,
while maintaining separate evidence for Gen1 and Gen2 behavior.

Exit gate: DQK is campaign-capable in the shared runtime and the native track completes a validated
campaign vertical slice with combat resume.

### P6: Authoring Beta

Import a representative FRUA module and create a complete small Greybox campaign using only released
authoring surfaces.

Exit gate: both packages pass validation and run in browser/Electron from a clean checkout/build.

### P7: Compatibility Release

Package the browser/Electron tools, generated support matrix, migration-safe saves/modules, and
reproducible native artifacts.

Exit gate: a clean-machine release test can discover user-owned installs and run every claimed route
without maintainer-local paths.

## Rolling Decomposition Rules

Use these rules when adding the substeps requested by an active milestone:

1. Keep program goals stable unless product scope genuinely changes.
2. Split the next unknown boundary, not every imaginable future task.
3. Every research step must name the decision or implementation it will unblock.
4. Every implementation slice must name its retail or synthetic verification evidence.
5. Record profile-specific differences explicitly; do not hide them in generic fallbacks.
6. Promote a game only when the corresponding compatibility-level gate is automated.
7. Update support/docs in the same slice that changes a capability claim.
8. Deploy only after engine tests, typecheck, production build, static browser smoke, and live checks.
9. When a slice reveals several independent unknowns, add them as separate queue items ordered by
   dependency and user value.
10. Keep completed evidence and failed hypotheses in research notes so later sessions do not repeat
    the same probes.

## Immediate Multi-Slice Program

The next work should build foundations that unlock several games rather than only adding isolated
screens:

1. **All-games corpus runner**
   - Combine binary maps, archive inventories, route probes, record-size/layout probes, and manifest
     coverage into generated JSON plus Markdown.
   - Feed the support matrix from this data or validate its claims against it.

2. **Natural encounter harness**
   - Discover cell/event entries that queue retail monsters and reach opcode `COMBAT`.
   - Capture encounter/reaction, explicit player combat choice, queued groups, active full 2D
     tactical setup, outcome, and resumed ECL state as separate checkpoints.
   - Apply first to Pool, CoAB, and Secret, then generalize.

3. **Savage Frontier format profile**
   - Recover Gateway/Treasures VGA DAX palette/pixel rules.
   - Locate combat-facing fields in Gateway's 422-byte and Treasures' 510-byte monster records
     instead of applying CoAB offsets.
   - Validate AD&D 2e rules and item/monster side tables before enabling combat.

4. **Persistent route proofs**
   - Attach save/import/export tests to each promoted natural route.
   - Prove map position, party state, flags, encounter outcome, and time survive reload.

5. **Decompiler depth in parallel**
   - Use the parsed VROOMM FIXUP TABLE to classify selector targets and finish selector-to-stub/
     resident routing; do not assume a second uniformly-strided resident segment.
   - Produce DQK/CKIT RTLink maps and runtime-vs-game-code separation.
   - Recover natural ECL-to-combat call chains for both engine generations.
