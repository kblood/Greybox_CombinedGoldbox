# Decompile Methodology — Krynn Trilogy DOS Executables

> **Status reviewed 2026-10-11:** the original June tool recipe below predates the shared
> mappers and successful Ghidra imports. Start with
> [decompiler-project-inputs.md](decompiler-project-inputs.md) and
> `tools/decompiler/README.md`. Gen1 uses `vroomm_layout.py`; Gen2 uses
> `rtlink_map.py` (13 DQK descriptors, 28 CKIT descriptors, with explicit boundary evidence).
> DQK dispatch and CoK/DoK RNG are recovered; see the updated §3 and worklist.
> Neither the original installation suggestions nor similarity to CoAB establishes a
> title's source language or semantic parity.

**Scope:** Reproducible pipeline for decompiling Champions of Krynn (CoK), Death Knights of
Krynn (DoK), and The Dark Queen of Krynn (DQK) DOS executables to readable C, enabling
clean-room engine verification and behaviour re-derivation.  
**Written:** 2026-06-24.  
**Primary sources:** `coab_extracted/` (Simeon Pilgrim's COAB C# reimplementation, the primary
Rosetta Stone); `tools/disasm_cok.py`; `tools/disasm_dqk.py`; Simeon Pilgrim's blog posts;
`docs/engine/research/decompilation-sources.md`; `docs/engine/research/disasm-combat-krynn-SUMMARY.md`;
`docs/engine/research/cok-copy-protection.md`.

## 1. How the COAB Decompile Was Produced

### 1.1 Primary tool: IDA Pro (full/commercial version)

Simeon Pilgrim used **IDA Pro** (an older, unspecified paid version — not IDA Free 5.0) to
produce the COAB decompile. The evidence from his blog
(https://simeonpilgrim.com/blog/2005/08/04/curse-of-the-azure-bonds-project/ ) is:

- **Binary loading:** COTAB.EXE was compressed/encrypted at rest. Pilgrim used DOS `debug.exe`
  inside DOSBox to single-step past the decompression stub, dump all 64 KB segments to screen
  by redirecting `debug.exe` I/O to a file, and wrote a C++ parser to convert the ASCII hex
  dump back to a binary flat image. The recovered flat image was then loaded into IDA.
- **Segment table reconstruction:** After loading the flat image, IDA's auto-analysis had
  incorrect segment boundaries. Pilgrim spent approximately a week manually rebuilding the
  correct segment table (mapping real-mode CS:IP layout, overlay spans, DGROUP) from the
  binary.
- **Overlay loading:** CoAB used `INT 3Fh` VROOMM stubs (the classic Borland FBOV mechanism)
  plus a separate overlay file. Pilgrim reused IDA IDC scripts he had written around 2000
  while working on Pool of Radiance to import the overlay file at the correct linear address
  and extend the IDA segment map accordingly.
- **FLIRT library-signature matching:** After loading, Pilgrim noticed Borland C runtime
  library functions were not named (FLIRT had not run). He reloaded the binary fresh and
  forced FLIRT to run. This automatically named hundreds of standard library functions
  (printf-family, string routines, memory management, math), leaving only game-specific
  functions unnamed. IDA ships Borland C/C++ DOS signatures natively (confirmed: IDA bundles
  Turbo C++ 1.01, Borland C++ 3.1, 4.0, 4.5, 5.0 .sig files for real-mode DOS targets).
- **Overlay jump fixup IDC script:** A separate IDC script (blog post 2010-07-23,
  https://simeonpilgrim.com/blog/2010/07/23/ida-script-fixing-overlay-jumps/ )
  scanned for all `CD 3F` stubs (each 5 bytes: `CD 3F <word proc_off> 00`), traced the
  far-jump chain to the actual function, and rewrote every cross-reference to point to the
  real target, eliminating hundreds of intermediate stub layers from the xref graph.
- **Translation to C#:** With a clean, named IDA listing (~110 K lines of annotated asm),
  Pilgrim manually translated functions segment by segment into C#, using Visual Studio regex
  to match common assembly patterns. The resulting C# preserves original `seg600:XXXX` /
  `sub_XXXXX` addresses in comments throughout. The Makefile at
  `coab_extracted/Makefile` shows the build: `gmcs` (Mono C# compiler) assembles
  `Classes/` and `engine/ovr002.cs`–`ovr034.cs` + `seg001.cs`–`seg051.cs`.
  File naming maps directly to the IDA segment/overlay naming (`seg001`, `ovr003`, etc.).

### 1.2 What the COAB artifacts in this repo actually are

| File/Dir | What it is | How it was produced |
|---|---|---|
| `coab_extracted/coab_new.idc` | IDA IDC script exporting **type/enum/struct definitions** only (`Enums()` + `Structures()`). Header: "generated by The Interactive Disassembler (IDA)". Contains charStruct, itemStruct, enum definitions with field names. | Exported from IDA database with `File → Produce file → Create IDC file` |
| `coab_extracted/coad_db.idc` | Full IDA database export: `GenInfo()` + `Segments()` + `Enums()` + `Structures()` + `Bytes()` + `Functions()` + `SegRegs()`. Contains all `seg000`–`seg051`, `stub001`–`stub036` segments with exact `SegCreate` calls and DS/SS values. | Same export path — the master segment/address map |
| `coab_extracted/coab_new.lst` | IDA listing: struct definitions in IDA `.lst` format (offsets, field names, sizes). The `charStruct` at offset 0x0000 with all field names visible. | Generated by IDA `Produce file → Listing` |
| `coab_extracted/engine/ovr*.cs` | Human C# translation of each FBOV overlay segment | Manual translation by Pilgrim |
| `coab_extracted/engine/seg*.cs` | Human C# translation of main-code (non-overlay) segments | Same |

**Key implication:** The `.idc`/`.lst` files confirm IDA Pro was used (not Ghidra). They are
reloadable: `coad_db.idc` can be fed to IDA (`-c` switch then `F2` → name the file) to
reproduce the exact segment layout Pilgrim worked from. This is the primary reproducibility
artefact.

### 1.3 What IDA Pro version is needed to reproduce COAB-style work

The COAB decompile predates IDA Free 5.0 (released ~2006). However:
- **IDA Free 5.0** (mirror: `https://downloads.scummvm.org/frs/extras/IDA/idafree50.exe`,
  sourced by ScummVM project) is the last freeware IDA that supports DOS MZ + FBOV overlays.
  It produces separate `ovr075`…`ovr153`-style segments from FBOV automatically. This has been
  confirmed to work with FBOV containers by the Ghidra issue tracker (issue #5543 references
  IDA Free 5.0 as the working reference implementation). **Limitation:** No decompiler (Hex-
  Rays decompiler requires paid IDA Pro 7+); output is pure annotated assembly.
- **IDA Home** (current, ~$499/yr) includes the DOS MZ loader and 16-bit real-mode support
  (confirmed by Hex-Rays community forum post, 2025). Includes the Hex-Rays decompiler for
  32/64-bit but **not** for 16-bit real-mode (no 8086 decompiler exists in any IDA tier as of
  2025). So even paid IDA gives annotated assembly for 16-bit DOS, not C output — C output
  requires manual translation (as Pilgrim did).
- **IDA Pro** (full, ~$3,500 one-time + $1,000/yr) adds non-x86 decompilers and more FLIRT
  sigs but no additional benefit for 16-bit DOS decompilation beyond IDA Home.

**Practical recommendation:** Use **IDA Free 5.0** for the FBOV overlay loading and initial
analysis; it is free, known to work, and produces the same segment structure Pilgrim used.
For iterative naming / struct work use modern Ghidra (free) in parallel (see §2).

## 2. Recommended Pipeline: DQK.EXE and CoK/DoK START.EXE + GAME.OVR

### 2.1 Binary structure (established facts)

| Game | Binary | Container | Our tools |
|---|---|---|---|
| CoK | `Champions of Krynn/START.EXE` (stub) + `GAME.OVR` (pool) | START.EXE: 61,607-byte packed MZ; unpack resident code with `tools/exepack_unpack.py` before analysis. The readable packed-image thunks do not establish an unpacked runtime. GAME.OVR: `FBOV` header + 35 overlay segments. `ovrsize = 0x00041adf`. | `tools/disasm_cok.py` with `overlays`/`resolve`/`thunk` subcommands. RE.5 validated 35 descriptors. |
| DoK | `Death Knights of Krynn/START.EXE` + `GAME.OVR` | Same FBOV structure. `ovrsize = 0x0003da2d`. | `tools/disasm_dok.py` — `overlays`/`resolve`/`thunk` ported 2026-07-01 (RE.7, `docs/engine/research/disasm-spells-krynn.md` §25); 35-descriptor table reconstructed from DoK's own bytes, validated with a 4-selector positive control. |
| DQK | `The Dark Queen of Krynn/DQK.EXE` (449,664 bytes) | MZ stub (header 0x2400 bytes, load image ends 0x218D5) + ~312 KB Borland overlay tail. NOT classic INT 3Fh — uses per-segment far-call vector tables. NO separate OVR file. | `tools/rtlink_map.py` + `tools/disasm_dqk.py`; mapped RTLink descriptors, vectors and boundary evidence. |

### 2.2 Step-by-step pipeline

**Step 1 — Acquire and verify binaries (already done)**

All three game folders contain the DOS/GOG releases. Binary structure confirmed by
`tools/disasm_cok.py info`, `tools/disasm_dqk.py --info`, and string searches:
- CoK/DoK: `FBOV` magic, `Portions Copyright (c) 1983,91 Borland`, INT 3Fh thunks in START.EXE.
- DQK: `MZ` header, `Cannot find overlay file` string in overlay tail, `eov0001:` through
  `eov0009:` (error-message numbering is not the descriptor count: `rtlink_map.py` maps 13 DQK overlays; HLIB GLB files hold data, not executable code).

**Step 2 — Use the reproducible import packages**

Run `python tools/export_decompiler_inputs.py --strict` and follow
`tools/decompiler/README.md` for `ghidra_import.py` / `ida_import.py`.
The supplied address model places each overlay in a separate synthetic 64 KiB slot in a
16-bit protected-mode analysis database; it does not claim those addresses are DOS runtime segments.
Ghidra imports and independent FID reopen/query checks are documented for all eleven packages.
IDA's real import gate remains unrecorded. For original-runtime tracing use the real-mode
segments and the title's mapper, rather than these synthetic database addresses.

**Step 3 — Apply Borland C FLIRT signatures**

In IDA: `File → Load file → FLIRT signature file`. Navigate to IDA's `sig/` directory.
Load the Borland C++ DOS signatures: look for `bcc.sig`, `bc31.sig`, `tcc.sig` (names
vary by IDA version). IDA 5.0 ships signatures for Turbo C 2.x, Borland C++ 3.1, 4.0, 4.5,
5.0 for DOS real-mode targets. Apply all Borland DOS variants; FLIRT will auto-name
standard library functions (string, memory, printf, math, file I/O). This is what Pilgrim
did and what converts ~30–40% of all function calls from `sub_XXXXX` to real names.

For Ghidra (parallel workflow — see §2.4): use the **ApplySig** script
(https://github.com/NWMonster/ApplySig ) to apply IDA FLIRT `.sig` files. Community
FLIRT signature databases (https://github.com/Maktm/FLIRTDB ,
https://github.com/push0ebp/sig-database ) may contain Borland C DOS variants.
Alternatively, generate `.sig` files from the actual Borland C++ 3.1 compiler library
`.LIB` files using IDA's FLAIR tools (`plb`/`pcf` → `sigmake`).

**Step 4 — Treat symbol absence as the documented baseline**

`krynn-toolchain-forensics.md` §5 records no `FB 49` TDS magic in the three held EXEs.
The old 'not checked' statement is superseded. That scan is evidence of no detected embedded
TDS block, not guaranteed original symbol recovery. The current import packages instead carry
same-game CoAB symbols and explicitly nonsemantic candidates. Do not promote sibling names
from a signature or field-shape match alone.

**Step 5 — Resolve overlays through the shared evidence mappers**

`tools/vroomm_layout.py` parses Gen1 descriptors/fixups and classifies routed calls,
retaining unresolved relocated selectors. This supersedes the old `0x200 + selector*16`
heuristic as the shared import basis. CoK/DoK resident analysis must use the unpacked image.
`tools/rtlink_map.py` handles the separate DQK/CKIT RTLink family; see
[rtlink-map-dqk-ckit.md](rtlink-map-dqk-ckit.md), including the 2026-10-02 DQK overlay-5
base correction. A descriptor map still does not name every function or resolve every runtime call.

**Step 6 — Use COAB as naming oracle**

With IDA's auto-analysis, FLIRT, and thunk resolution complete, the next step is to apply
names from COAB. Process:

1. Load `coab_extracted/coad_db.idc` into IDA (press `F2`, enter path) after loading the
   Krynn binary. The IDC recreates the COAB segment layout including segment names
   (`seg001`–`seg051`, `stub001`–`stub036`). **Do not run it blindly** — the COAB segment
   addresses differ from the Krynn binaries. Instead, use it as a naming reference: when
   IDA shows an unnamed function at address X, search `coad_db.idc` or the C# sources for
   the corresponding COAB function to borrow its name.
2. Use `coab_extracted/coab_new.idc` to import the **type definitions** (charStruct,
   itemStruct, enums for race/class/spell/money). Study their `Structures()` and `Enums()` definitions, then verify every field against the
   target title before applying it. CoK and DoK also differ from CoAB; DQK has another
   record layout (verified
   in `docs/engine/research/disasm-combat-krynn-SUMMARY.md`).
3. Work function-by-function: locate a function in CoK by string-xref anchoring (the method
   in `tools/disasm_cok.py`), compare to the named COAB equivalent in `ovr003.cs`/`ovr018.cs`
   etc., assign the name in IDA. Use the `seg600:XXXX` comments in COAB's C# to correlate.

**Step 7 — Use Ghidra for parallel analysis (optional but recommended)**

Ghidra 11.x (free, Apache 2.0, https://ghidra-sre.org/ ) with **GhidraDosToolbox**
(https://github.com/Gravelbones/GhidraDosToolbox ) provides:
- DOS MZ loader with PSP/IVT and interrupt mapping
- Language ID: `x86:LE:16:Real Mode:default`
- Interrupt function name overlays (INT 21h, etc.)

**FBOV overlay caveat (critical):** Ghidra does NOT natively parse FBOV/VROOMM overlays
(confirmed open issue #5543, status "Future", last updated 2023). The FBOV tail is reported
as "extra bytes." To work around: write a Ghidra loader script that reads the DESCS table
from `tools/disasm_cok.py` and adds memory blocks for each overlay segment, then marks
functions at overlay entry points. This is extra work but Ghidra's type propagation, stack
analysis, and free decompiler output (pseudo-C for 32-bit; 16-bit produces assembly-like
pseudo-C with limitations) make it worthwhile as a second opinion.

**ApplySig** (https://github.com/NWMonster/ApplySig ) applies IDA `.sig` files in Ghidra.
The Borland sigs from IDA Free 5.0's `sig/` directory can be copied into Ghidra this way.

**Step 8 — Spice86 for dynamic verification**

**Spice86** (https://github.com/OpenRakis/Spice86 ) is a real-mode DOS emulator that
instruments execution: it builds a Control Flow Graph from actual run-time traces and generates
a self-contained C# project (`CfgGeneratedOverrides.cs`) as a mechanical assembly→C# skeleton.
This is a complementary approach to IDA static analysis:

1. Run the target game in Spice86.
2. Trigger the specific game path (e.g., combat, save/load).
3. Spice86 emits a CFG-derived C# file where each basic block becomes a method stub.
4. Compare the emitted structure to the COAB C# and to `tactical.ts` / other engine code.
5. Use as a **diff oracle** to catch discrepancies.

**Caveat:** Spice86 requires the game to actually run through its overlay loader; if the Borland
VROOMM runtime does not load correctly in the emulator, overlays will not execute. UNKNOWN
whether Spice86's DOSBox-derived emulation is faithful enough to run CoK/DoK/DQK fully.
Testing is required. Spice86 output is mechanical C# (not readable prose); it serves as a
starting point, not a finished decompile.

## 3. Biggest Obstacles and Mitigations

### 3.1 DQK RTLink mapping — recovered, with scoped boundary limits

`rtlink_map.py` maps the resident MZ image, descriptor table, 13 integrated DQK overlays
and resident vector stubs; CKIT has 28 descriptors with approximate/unknown boundaries
kept explicit. This supersedes the original 'unsegmented tail' blocker. DQK is RTLink/Plus,
not the Gen1 VROOMM selector scheme. Executable overlays live inside DQK.EXE; HLIB libraries
contain game data.

`rtlink-map-dqk-ckit.md` records the evidence for each prefix. The 2026-10-02 overlay-5
base correction to `0x3a4c0` shows why every new CS-relative table needs its own boundary
check. A mapped/importable image is not a complete semantic decompile.

### 3.2 DGROUP data-segment binding — title-local bases now exist

Recovered consumers identify CoK's unpacked DS paragraph `0xBC6`
(`cok-retail-rest-contract.md`), DoK's `0xBCE` (`dok-rng.md`), and DQK's canonical
`0x322E` (`tools/unicorn_dqk_trace.py`, `DQK_DGROUP_SEG`). Runtime load relocation must
still be accounted for. These do not bind every overlay variable to a semantic name.

Use unpacked image-relative addresses, canonical segments and observed live addresses
explicitly; do not mix them with the synthetic decompiler slots. A new `DS:imm16` claim
still needs the correct title/base and a verified reader/writer.

### 3.3 Missing symbols (unnamed functions after FLIRT)

After FLIRT runs, game-specific functions remain unnamed. Pilgrim estimated ~110 K lines
of assembly for COAB; the Krynn binaries are comparable. The COAB C# provides ~3,000+
named functions as a naming oracle, but the mapping is not automatic — function signatures
must be matched by:
- String-xref anchoring (already the method in `disasm_cok.py`)
- Struct-field offset matching (COAB's charStruct offsets vs Krynn offsets, which DIFFER
  per game — see `disasm-combat-krynn-SUMMARY.md` for confirmed offset divergences)
- Calling-convention matching (Borland `__pascal` for engine code: look for `RET n` on
  callee-cleanup, positional args in left-to-right push order; `__cdecl` for C standard lib)

**Mitigation:** Maintain a per-game offset-mapping table (analogous to the already-built
`ROUTINES` dict in `disasm_cok.py`). Focus naming effort on the ~20 highest-value functions
(ECL VM dispatch, combat to-hit, death handler, save/load, GEO loader) rather than full coverage.

### 3.4 ECL opcode drift — dispatch mapped, title-local semantics still matter

DQK's direct-indexed near-pointer table is canonical `2033:0d34`, file `0x032a54`,
with 66 slots `0x00`–`0x41`. Handler-prefetch inspection corrected operand counts;
`0x31` is a counted short menu, and `0x41` has a bounded original XP-write proof.
See [decompile-dqk-ecl-dispatch.md](decompile-dqk-ecl-dispatch.md).

This replaces the old recipe describing all dispatchers as sparse triple/far-pointer tables.
Numeric agreement does not establish matching framing or host effects: use the title's dialect.
A live DQK COMBAT handoff and safe native QSV persistence remain open.

## 6. Current implications — reviewed 2026-10-11

Use reproducible mapper/import output rather than repeating the original loader setup.
Ghidra import/FID checks are recorded in `tools/decompiler/README.md`; an IDA smoke import
remains a separate gate. CoAB is a same-game symbol oracle and a behavioral comparison source,
not permission to import names, record offsets or rules into other titles without evidence.

The primary deliverable is the native DOS Greybox engine; the web implementation is secondary
and already exists. Recovered specifications, engine helpers, product callers and original
runtime parity are distinct milestones. The old claim that a targeted loop exhausted the
decompile work is too broad: see the current worklist and title-local follow-ups.
