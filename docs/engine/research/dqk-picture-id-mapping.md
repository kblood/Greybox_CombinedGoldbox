## Gap 2: `PICTURE` id -> `PICA`/`PICB`/`PICC.TLB` slot — SOLVED

### Method

`docs/hlib-format.md` §1c already documents (from earlier, unrelated HLIB format-RE work)
that a **MASTER** `HLIB` container's `ptr[0]` (only present when `magic == 1`) is a
"set-id table":

```
WORD count
count x { WORD id, WORD ptrIndex }   // ptrIndex is 1-based into the container's pointer list
```

That doc explicitly noted the existing decoders (`decodeHlib`, `mapHlibMasterSlots`)
**ignore this table and walk pointers positionally** — it was recorded as spec but never
used for a reverse (id -> slot) lookup. It is exactly the mapping this gap needs.

`docs/engine/research/dqk-demo-route.md` §4 independently corroborates that this is the
*real* mechanism DQK's own loader uses: its `--trace-asset-reads` dynamic trace of the
`ECL.glb`/`GEO.glb` opens shows "a 6-entry linear scan of the set-id table at file offset
0xd4" before the actual seek/read — i.e. DQK.EXE itself resolves ECL/GEO member ids via
this exact table shape. `PICA`/`PICB`/`PICC.TLB` are the same MASTER-HLIB container type,
so the same table applies to them; no new dynamic trace was needed to establish this,
only to apply it.

### Implementation

New production functions in `packages/engine/src/loaders/hlib.ts` (exported from
`packages/engine/src/index.ts`):

- `parseHlibSetIdTable(bytes, base = 0): Map<number, number>` — parses the id -> ptrIndex
  table directly (returns an empty map for non-`magic=1` / leaf containers).
- `dqkPictureSlotImages(bytes, setPtrIndex): HlibImageMember[]` — decodes every image in
  the sub-container at a given pointer index.
- `dqkPictureSlot(bytes, setPtrIndex): HlibImageMember | null` — convenience: first image
  of that sub-container (portraits are single-image sets).

### Visual verification

Rendered each resolved slot to PNG (`renders/dqk-demo-pictures/`, regenerated by the test
above) and inspected them directly:

- id 90 / 91 — a horned/scaled draconic face, consistent with the script's "MY BROOD"
  dragon-villain narrator addressing its followers.
- id 115 — a small, round-faced character consistent with "the infantile kender" line.
- id 149 — a fair-haired, pointed-ear portrait consistent with "despised elves".
- id 170-173 — human/knight-style armoured portraits, consistent with "these so-called
  champions" / "their deeds were noble" lines about the party's past allies/enemies.
- id 239 — solid black in every occurrence. Given it is *always* the picture immediately
  preceding each new named portrait in the script (see the `PICTURE #239` / `PICTURE #nnn`
  pairs in `dqk-demo-route.md` §5), this is confidently a deliberate blank/fade frame, not
  a decode failure — every other id in the same libraries decodes to real art with the
  same code path, so a systematic bug would not selectively affect only id 239.

All portraits are narratively appropriate to their script context — strong independent
confirmation the id mapping is correct, not just structurally plausible.

### Wiring

`apps/web/src/ui/dqkDemo.ts`: `flattenEffects` now captures `picture` effects into the
beat stream; a `DqkPictureIndex` class (built from `PICA/B/C.TLB` fetched at demo start)
resolves each `pictureId` via `parseHlibSetIdTable` + `dqkPictureSlot`; `tick()` paints the
resolved image to a dedicated `<canvas>` (`paintPicture`, using `indexedToRGBA`) as each
`PICTURE` beat plays, hiding the canvas when a beat has no resolvable art.

### A negative result worth recording (method, not content)

An initial attempt correlated the *order* of `PICx.TLB` open events in a `--trace-asset-reads`
Unicorn dynamic trace (`build/dqk-load1000-title-D-picio.log`, a fresh 21M-instruction rerun)
against the picture-opcode sequence from a pure-VM simulation of the script
(`239,91,239,170,239,171,...`). This produced a contradiction — id 239 appeared to open
PICC, then PICC again, then PICB, then PICA across its repeated occurrences, which is
impossible if 239 maps to one fixed slot. The assumption (that DOS's real execution order
of file opens matches the VM simulation's effect-emission order 1:1) does not hold, likely
because the real game's handling of the `8060: GOTO cbf:0` nonlocal jump differs from how
the pure block-scoped VM approximates it (fall-through). This approach was abandoned as
unsound rather than forced to a conclusion; the static set-id-table method above gave a
clean, unambiguous, fully self-consistent answer instead and superseded it. Recorded here
per this project's "UNLOCATED beats invention" ethic — applies to ruling out unsound
methods, not just to withholding invented content.

## Gap 1: `COMBAT` roster — re-characterized, then RESOLVED

> **2026-07-21 update:** the "still UNLOCATED" framing below is superseded —
> `docs/engine/research/dqk-duel-setup-dispatch.md` traces the native `CALL 0x0001` dispatch to
> DQK's "duel setup" combatant-cloning routine (structurally + literally cross-verified against
> COAB's decompiled `SetupDuel(bool)`), and a live Unicorn trace of the real Demo route captured
> the actual `CPIC.TLB` combat-icon ids DQK.EXE resolves for this script. `apps/web/src/ui/dqkDemo.ts`
> now renders those 5 real icons when `COMBAT` fires. The one remaining honest gap: DQK's own data
> ships no species/monster *name* for a CPIC icon, only its pixel art — see that doc's §6. The text
> below is kept as the original record of the re-characterization step.

### The original gap note was wrong on specifics

The demo player's original gap note attributed the unknown roster to "`GEO.GLB` id 26 has
no Gen2 map decoder yet". This is **false**: `packages/engine/src/loaders/geo.ts`'s
existing `decodeGen2GeoArchive` decodes id 26 without any changes — a 22x22 map, cells
populated normally. See `packages/engine/test/dqkDemoCombatRoster.test.ts` ("GEO.GLB id 26
... decodes cleanly — the map format is NOT the blocker"), which pins this as a permanent
regression guard so the claim cannot silently regress back into the gap note.

### The real, narrower blocker

Running `ECL.GLB` id 7 through the real `EclVm` (Gen2 dialect), auto-answering the
`PARLAY` menus the same way the demo player itself does, reaches `res.status === 'combat'`
with:

- `combat.monsters` — **empty array**. No `LOAD_MONSTER` opcode is reachable anywhere in
  block 7's bytecode (confirmed by inspecting the full disassembly in
  `dqk-demo-route.md` §5 — there simply isn't one).
- Immediately after the first `PARLAY` (`8056`), the script hits `8060: GOTO cbf:0` — a
  **nonlocal** goto: `cbf:0` is outside block 7, so the VM (which only interprets one
  block at a time) correctly cannot follow it and emits an `unhandled` effect
  (`GOTO(nonlocal)`) rather than crashing or guessing.
- In the reachable continuation, the script fires **five identical native
  `CALL 0x0001` dispatches**, which `packages/engine/src/ecl/vm.ts`'s
  `ECL_CALL_ROUTINES` table already names `setupDuelAttack` (prior RE work, not new to
  this pass).

So the true mechanism is: DQK's own native x86 code implements a "duel" combat-setup
routine (`CALL 0x0001`), and the roster this specific encounter uses is built by that
native routine, not by ECL `LOAD_MONSTER` data. This is not unique to the demo script —
the same `CALL 0x0001` routine is dispatched by `ECL.GLB` blocks 16, 36, 39, and 42 too
(grep `ECL_CALL_ROUTINES` usage / block disassembly for confirmation).

### Why this is being left open rather than solved

This project has already spent many dynamic-trace rounds trying to pin DQK's native
`COMBAT`-dispatch mechanism for the *simpler* case (an ordinary script whose combat is
driven by `LOAD_MONSTER` data) — see `docs/engine/research/decompile-dqk-ecl-dispatch.md`,
`docs/engine/research/combat-trigger-c4.2b-2b-2b.md`, and
`docs/engine/research/dqk-palanthas-palace-combat-route.md` — and that narrower problem is
still not fully closed. The demo's `CALL 0x0001 setupDuelAttack` mechanic is a *different
and additional* layer on top of that (a native "duel setup" routine, not just a native
combat trigger), so fully reverse-engineering what roster it actually builds is at least as
hard, with no proven starting point. Per this project's "UNLOCATED beats invention" ethic,
`apps/web/src/ui/dqkDemo.ts` leaves the roster genuinely absent — an explicit
`COMBAT_GAP_NOTE` message is shown instead of a fabricated fight — and this doc records the
precise mechanism now known to be responsible, narrowing (but not closing) future work.

### Evidence / regression test

`packages/engine/test/dqkDemoCombatRoster.test.ts` — asserts, against the real DQK GOG
install: the empty roster, the 5x `setupDuelAttack` calls, the nonlocal `GOTO`, the
`LOAD_FILES #26` target, and that `GEO.GLB` id 26 decodes cleanly (guards against the false
"no map decoder" claim regressing).
