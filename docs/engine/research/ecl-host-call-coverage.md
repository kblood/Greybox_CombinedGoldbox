## Headline: recorded-only work and vacuous CALL handling

This tool finds two separate gaps between what CoK's and DoK's retail ECL scripts ask the native VM (`native/src/ccecl.asm`) to do and what the VM applies:

1. **The placeholder-recorder gap (this section, the PRIMARY finding).** Ten opcode byte values -- `PRINT`, `PRINTCLEAR`, `DELAY`, `PICTURE`, `PRINT_RETURN`, `TREASURE`, `CLEAR_BOX`, `ROB`, `SHORT_MENU`, `UNKNOWN_1F` -- all dispatch to `op_script_effect`. Read in `native/src/ccecl.asm`, that handler writes `cur_op` and its dialect-adjusted operands into `fx_script_events`, bumps `fx_script_count`, sets `FX_HAVE_SCRIPT`, and returns. It is a RECORDER, not an implementation: dispatch succeeds, decode is correct, control flow is preserved, and **nothing else happens**. No text prints, no box clears, no picture shows, no delay elapses, no treasure is granted, no item is stolen, no menu appears. This is the game's dialogue, its cutscene art, its pacing, and its loot.
2. **The `op_call` vacuous-dispatch finding (below, SEPARATE).** `CALL` (0x2D) has its own real handler, `op_call`, which does NOT go through `op_script_effect` at all -- but that handler's internal seven-way routine-id sub-dispatch selects between two byte-identical code paths, so it too never actually branches on which host routine was requested.

`op_award_xp` applies each title's verified transient-GBPR XP behavior: CoK's eligible party split and DoK's per-member class-slot split with a CCPARTY threshold cache.

A metric that asks only whether an opcode reaches a non-default handler cannot see either recorded-only effects or `op_call`'s incomplete routine-id work. Dispatch coverage is Champions of Krynn 1.000, Death Knights of Krynn 1.000; retain it only as a narrower control-flow measure.

## Scope and what this does NOT establish

- Static source-text analysis of `native/src/ccecl.asm` plus static CFG decode of retail `ECL{1,2,3}.DAX` bytes. No DOSBox/emulator run, no debugger, no runtime trace backs any number here.
- "Applied" means the opcode reaches a handler that is neither `op_default` (no handler at all) nor `op_script_effect` (the placeholder recorder). It does NOT mean the handler is semantically correct or complete -- only that it is not KNOWN to be a no-op recorder. `op_call` is the one exception known to also do nothing useful despite not being `op_script_effect`; it is called out separately below rather than folded into "applied", and is excluded from the applied/placeholder split's denominator by neither -- it still counts as "applied" in that split because this tool's placeholder-detection is a handler-identity check, not a semantic one, and `op_call`'s vacuity was found by a different, targeted proof (comparing its own two branches), not by the placeholder rule. Treat `applied` as an upper bound on real implementation, not a certificate of it.
- CFG reachability from the five documented ECL header entry points (`vm_run_1`/`search_location`/`pre_camp_check`/`camp_interrupted`/`initial_entry`), not from a save-file-seeded runtime walk. An instruction reachable only via a GOTO/GOSUB target this tool cannot resolve statically (a non-immediate/dynamic operand) is undercounted, not overcounted -- see each block's `truncated_offsets`.
- Only CoK and DoK are measured (this item's scope). The dispatch-map extraction in part (a) covers the full 0x00-0xff byte range, including Buck/Pool-only extended opcodes (0x42-0x4c, 0xa1) that never appear in CoK's or DoK's own corpus and are reported as having-a-handler-but-unused rather than omitted.

## Methodology-discrepancy demonstration (opcode byte 0x41)

**This section changed meaning on 2026-09-10 and the previous framing is quoted, not deleted, because it is what a returning reader will expect to find.** It used to open: "0x41 is not in CoK's or DoK's own opcode table (`OPCODES` covers 0x00-0x40 only, and neither profile has an extended-opcode override for 0x41), so a reachable landing on that byte value is an `unknown_opcode_byte_count`, not a decoded occurrence -- this tool is honest that it does not know what 0x41 means in this dialect." The first clause is still true (`OPCODES` really does stop at 0x40); the second is now FALSE. Both Gen1 titles now carry a grounded extended-opcode definition for 0x41 (`GEN1_AWARD_XP`, two operand words), read from each title's OWN retail `GAME.OVR` handler prefetch idiom rather than fitted to the corpus, so 0x41 DECODES and its sites are real decoded occurrences.

That matters for what this table is allowed to claim. The comparison quantity is now the CFG-reachable DECODED OCCURRENCE count. The old quantity -- unknown-opcode-byte landings -- is published beside it and now reads 0 for both titles **by construction, not by measurement**: a decoded opcode can never appear in `unknown_opcode_landings`, so comparing a naive scan against it would be a demonstration that can no longer fail. The point it was built to make survives the change intact: a naive raw-byte scan (`bytes.count(bytes([0x41]))` over each ECL block, ignoring instruction boundaries and reachability entirely) still overcounts by roughly 15-19x, because it also counts 0x41 wherever it happens to fall inside another instruction's operand words, and it counts unreachable blocks too:

| profile | naive raw-byte-scan count | CFG-reachable decoded occurrences | unknown-byte landings (0 by construction since 0x41 decodes) | overcount factor |
|---|---|---|---|---|
| champions-of-krynn | 617 | 33 | 0 | 18.7x |
| death-knights-of-krynn | 843 | 56 | 0 | 15.1x |

**Independent corroboration:** `docs/engine/research/gen1-opcode-41.md`'s own from-scratch reachability walker (a separate Python port, not this tool) reports CoK = 33 reached `0x41` sites; this tool's CFG-reachable landing count for CoK is 33 -- **a match, two independent implementations agreeing exactly.** That doc's DoK figure (50) does not match this tool's DoK figure (56), but the doc itself discloses why: its own scratch walker found residual desyncs from simplified GOSUB/GOTO handling on DoK specifically, and says explicitly this does not affect its CoK number. The DoK mismatch is a disclosed limitation of that document's own walker, not evidence against this tool.
